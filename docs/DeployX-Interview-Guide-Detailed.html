1. Executive Summary

DeployX is a mini Platform-as-a-Service product. It gives a developer a workflow similar to a simplified Render, Railway, or Heroku: connect a source repository, create a project, trigger a deployment, watch logs, receive a URL, and roll back a previous release.

The project is valuable as an SDE portfolio system because it is not only a CRUD website. It demonstrates a control plane, asynchronous job execution, durable state transitions, container orchestration concepts, access control, operational visibility, and deployment automation.

One-sentence pitch: DeployX turns a public Git repository into a monitored Docker deployment through an authenticated, asynchronous, production-style control plane.

2. The User Problem

Small teams often have application code but do not want to manually manage servers, runtimes, ports, logs, health checks, and failed releases. Existing cloud platforms solve this problem, but building a smaller version is an excellent way to understand what happens behind the button labelled “Deploy”.

3. Product Workflow

  1. User registers or logs in and receives a signed JWT.
  2. User creates a project with a name, HTTPS GitHub/GitLab URL, and branch.
  3. User starts a deployment. The API checks project ownership.
  4. The API writes a deployment row with status QUEUED, an initial log, and an audit event.
  5. The API publishes the deployment ID to RabbitMQ and returns without waiting for Docker.
  6. A worker consumes the message. Redis provides a short-lived processing lock.
  7. The worker clones the repository, checks the Dockerfile, builds an image, starts a resource-limited container, and probes its health path.
  8. The deployment becomes READY or FAILED.
  9. The dashboard polls status and loads persisted logs.
  10. The user can open the app, stop it, or roll back to a previous ready version.

5. Backend Design

The backend is a modular monolith. Packages are organised around business capabilities rather than technical layers:

com.deployx
  auth/          registration, login, current user
  user/          user entity and role
  project/       project creation and ownership
  deployment/    deployment lifecycle, logs, rollback
  worker/        queue publishing, consumption, execution
  audit/         security-relevant activity records
  common/        API errors and JWT security
  infrastructure/health endpoints

This design is intentionally simpler than starting with many microservices. The queue boundary gives a clean extraction path for a standalone worker later.

9. How DeployX Differentiates

DeployX is not positioned as a replacement for mature cloud platforms yet. Its differentiation is educational, architectural, and potentially operational:

  • Transparent control plane: the full deployment lifecycle is visible in code, making it useful for learning and technical interviews.
  • Self-hosted direction: the architecture targets an affordable Linux VM rather than requiring a proprietary cloud platform.
  • Deliberate distributed-systems learning: RabbitMQ and Redis are not hidden behind a managed service; their roles are explicit.
  • Security and ownership focus: project/deployment access is tied to authenticated users and ownership checks.
  • Extensible deployment engine: the worker boundary can later support buildpacks, multiple runtimes, private repositories, or Kubernetes.
  • Portfolio transparency: the product demonstrates how a PaaS works internally instead of only presenting a polished deployment button.

Honest positioning: do not claim DeployX beats Heroku or Render on scale, reliability, or feature breadth. Say that it is a focused, self-hostable deployment control plane and a demonstrable foundation for those capabilities.

10. Deployment State Machine

QUEUED -> BUILDING -> READY
                  \-> FAILED
READY -> STOPPED
READY -> SUPERSEDED
  • QUEUED: durable request accepted.
  • BUILDING: a worker owns execution.
  • READY: application passed its HTTP readiness check.
  • FAILED: pipeline error stored with message and logs.
  • STOPPED: container was intentionally removed.
  • SUPERSEDED: another release replaced this active version.

11. Security Model

  • Passwords are hashed with BCrypt and never stored in plain text.
  • JWTs provide stateless authentication for API calls.
  • Project and deployment queries include the authenticated owner ID.
  • Repository URLs are constrained to HTTPS GitHub/GitLab patterns in the current MVP.
  • Health and metrics are public for infrastructure scraping; business endpoints require authentication.
  • Docker workloads use memory and CPU limits. Production hardening should isolate networks and avoid exposing the Docker socket to workloads.

14. Interview Questions and Strong Answers

Why is deployment asynchronous?

Builds and health checks are slow and unpredictable. The API should acknowledge intent quickly, while RabbitMQ provides durable handoff and the worker owns long-running execution.

What happens if a message is delivered twice?

Redis uses a deployment-specific TTL lock. The first worker acquires it; later consumers skip processing. PostgreSQL remains the durable state source.

What happens if the worker crashes?

The deployment remains visible in PostgreSQL. A production version would add a lease/heartbeat and a recovery scheduler that requeues stale BUILDING records.

Why not use Kubernetes?

Kubernetes solves large-scale scheduling but adds substantial operational complexity. Compose and Docker are appropriate for the first single-VM milestone. The worker abstraction leaves room for a Kubernetes executor later.

How would you scale it?

Run multiple stateless API instances behind a load balancer, scale workers horizontally from RabbitMQ, use managed PostgreSQL and Redis, store images in a registry, allocate stable hostnames through a proxy, and add rate limits plus quotas.

What is unfinished?

The current RabbitMQ consumer is packaged with the API process; extracting it into a standalone worker is the next step. Stable hostname routing, stronger container isolation, real container replacement on rollback, TLS, backups, and managed secrets are also production follow-ups.

15. Product Sales Pitch

DeployX gives small teams a simple path from repository to running service without asking every developer to become a deployment-infrastructure expert. It combines repository-based deployment, Docker isolation, asynchronous builds, logs, health checks, rollback state, and monitoring in a self-hostable workflow. Its architecture is transparent and extensible, so teams can begin on one affordable VM and evolve toward dedicated workers, managed databases, registries, and stronger routing as usage grows.

16. Current Limitations and Roadmap

  1. Extract the worker from the API into a dedicated process/container.
  2. Move images to a private registry and support immutable image promotion.
  3. Replace random ports with stable hostname routing through a proxy.
  4. Implement true rollback by stopping and re-routing containers.
  5. Add stale-job recovery, retries, rate limits, quotas, and cleanup policies.
  6. Add Testcontainers, frontend tests, and end-to-end CI.
  7. Add GitHub App/OAuth integration and private repositories.
  8. Deploy to a Linux VM with TLS, backups, firewall rules, and secret management.

17. Closing Statement

“I designed DeployX as a deployment control plane rather than just a dashboard. The API handles identity, ownership, durable deployment state, and job publishing. RabbitMQ decouples user requests from expensive work, Redis provides idempotency coordination, and the worker handles cloning, building, running, and health checks. PostgreSQL is the source of truth, Docker isolates workloads, Nginx provides a single edge, and Prometheus/Grafana provide visibility. I started with a modular monolith to keep the first version understandable, but the queue and worker boundary make the system ready for independent scaling.”
